Mongoose ديال survey: subdocs و relationship fields

الدفع والـ deploy سالاو — دابا نصاوبو الـ heart ديال المنتوج: الـ schema ديال الـ survey، ونتعلّمو فين نستعملو subdocument وفين relationship field.

~13 دقايق · Quiz ديال retrieval فالأخر

Win ديال هاد الدرس غادي تصاوب Survey schema صحيحة: recipients كـ subdocuments باش ما يوقعش التصويت المكرر، _user كـ relationship field باش تعرف شكون مالك، وroute handler محطّب بـ requireLogin + requireCredits. هادي هي الـ data modeling اللي كتفرق بين prototype و production.

1 · الـ route الأول: POST /api/surveys

الكورس كيقسم الـ survey feature لـ3 routes (إنشاء، جلب القائمة...) ونصيحة هي: عزل route وحدة وجرّبها قبل ما تكمل البقية، ومن بعد رجع للـ front end.[2] الـ route ديال الإنشاء كيمسّ الـ express route handler، و React front end، و MongoDB — نفس الـ request وحدة.[3]

وأول مشكل كيتصطدم بيه: فين نخزّنو feedback (شكون قال yes وشكون قال no)؟ وإذا خزّناها مكررة، نفس الـ user يقدر يصوّت بزاف ديال المرات.[3] الحل هو الـ subdocument collection.

2 · علاش recipients داخل الـ survey: subdocument collection

الـ recipients كيسكنو كـ list داخل الـ survey نفسو، وكل واحد عندو email (String) و responded (Boolean) بـ default: false — يعني حتى واحد ما يصوّت قبل ما يclicki.[4][5]

وقاعدة الاختيار هي: subdocuments كنستعملوهم ملي بغاو association واضح وstrong بين جوج records. الـ recipient ماعندو حتى معنى بلا الـ survey ديالو — يعني ملكية واضحة (ownership).[4]

ولكن علاش users ما عندهمش list ديال surveys كـ subdocuments؟ حيت عند MongoDB limit ديال 4MB لكل document. بـ20 bytes للمتوسط ديال email، وحدة survey كتتّسع لـ تقريباً 200,000 emails — مقبول. ولكن إلا حطينا surveys كاملة داخل user، نفس الـ user كيغلق عندو 200,000 emails ديال surveys كاملين... والمشكل كيولي شي super user كيصرف فلوس وما يقدّرش يزيد.[4]

نتيجة كتجي غلط حطيتي surveys كاملة داخل user document: أول ما واحد يزيد آلاف الـ recipients، الـ document كيقرّب من limit ديال 4MB وكيرفض الكتابة. الحل: recipients داخل survey كـ subdocuments، والربط مع الـ user عبر _user كـ reference field. 
// models/recipient.js
new Schema({ email: String, responded: { type: Boolean, default: false } });

3 · relationship field: شكون مالك الـ survey؟

باش نعرفو أي user صاوب أي survey، كنزيدو _user على الـ survey schema:[6]

_user: { type: Schema.Types.ObjectId, ref: 'user' }  // ref بـ lowercase
  • Schema.Types.ObjectId = الـ ID ديال الـ user owner. الـ ref: 'user' كيقول لـ Mongoose بلي هاد الـ reference كيتبع الـ users collection.[6]
  • الـ underscore ماشي إجباري — غير convention باش أي حد يشوفو يفهم بلي هادا reference field ماشي data عادية.[6]
  • وزدنا dateSent و lastResponded بـ Date — ماشي ضروريين للـ app، ولكن كيعطيو لـ owner فكرة واش الـ survey مازال active.[6]

الخلاصة بجوج كلمات: subdocument يعني البيانات ساكنة لداخل — الـ recipients جزء من الـ survey وما كيتنقلوش بوحدهم، وrelationship field يعني غير كنخليو إشارة — الـ _user كيقول هاد الـ survey ديال شكون بلا ما ننسخو الـ user كامل. علاش هادي مهمة ملي تخدم لـ client: حيت الـ client كيخلص على بيانات نقية ما فيها لا تصويت مكرر لا بحث ثقيل ملي كيكبر المشروع.

subdocumentrecipients فـ models/recipient.js: { email: String, responded: false } — ساكنين لداخل ديال الـ survey، وكل responded كيتحفظ مع الـ survey ديالو.
relationship field_user فـ models/survey.js: { type: Schema.Types.ObjectId, ref: 'user' } — غير إشارة خفيفة لـ users collection.

كيفاش تقرا هاد المخطط: قارن العمودين — شوف فين ساكنة البيانات وشوف شنو كيربط الـ collections.

بأي مثال الـ _user بحال رقم بطاقة التعريف المكتوب على ملف: خفيف وغير كيشير لشكون مول الملف بلا ما تنسخ الملف كامل. أما الـ recipients بحال الوراق اللي لداخل ديال نفس الملف: ما عندهم حتى معنى خارج الملف ديالهم.

4 · الحماية والتنفيذ: requireLogin ثم requireCredits

الـ Survey model خاصو يتطلب من index.js (و Recipient كيتطلب من survey.js راسو)، ومن بعد كنصاوبو ملف جديد routes/surveyRoutes.js فيه app.post('/api/surveys', ...).[7]

قبل الـ handler، كنزيدو requireCredits — ملف جديد كيتنسخ من requireLogin ويتبدّلو فيه غير الـ if statement: req.user.credits < 1 كيرجع 403 مع رسالة "not enough credits" (الـ 402 payment required موجود فـ spec ولكن reserved for future use).[8] علاش middleware ماشي داخل الـ handler؟ حيت ممكن نحتاجو نفس الفحص فـ routes أخرى فالمستقبل.[8]

app.post('/api/surveys', requireLogin, requireCredits, handler);
// 1) مسجّل؟  2) عندو credit؟  3) صاوب الـ survey

الترتيب مهم: خاص الـ user يكون مسجّل قبل ما نطلبو منو credits، والجوج قبل ما نديرو أي logic.[8] من بعد، فالـ handler: const survey = new Survey({ title, subject, body, recipients: [...] }) — Mongoose كيصاوب الـ subdocuments راسو من غير ما نعرفوهم.[10]

  1. Browser → requireLogin POST /api/surveys كيدخل لـ requireLogin اللي كيقلب على req.user
  2. requireLogin → requireCredits requireCredits كيقرا req.user.credits وإلا كان < 1 كيرجع 403
  3. requireCredits → handler الـ handler كيصاوب new Survey({ title, subject, body, recipients })
  4. handler → MongoDB survey.save() كيحفظ فـ surveys collection مع recipients كـ subdocuments

كيفاش تقرا هاد المخطط: تبع الأرقام من الـ Browser حتى لـ MongoDB — كل سطر فيه شكون صيفط لشكون وشنو وقع بالضبط.

recipients: emails.split(',').map(email => ({ email: email.trim() }))  // trim قبل

5 · ممارسة retrieval

جاوب من راسك قبل ما تclicki. ما تقدرش تحل حتى تجاوب — هادي هي القوة اللي كتبني memory.

1. علاش حطينا recipients كـ subdocument collection داخل survey؟

الـ subdocuments كنستعملوهم ملي بغاو ownership واضح: الـ recipient ماعندو حتى معنى بلا الـ survey ديالو، وهكذا كل تصويت مسجّل مع الـ survey ديالو.[4]

2. شنو كيوقع إلا user عندو zero credits و بغى يصاوب survey؟

الـ middleware كيتسلّم الـ request قبل الـ handler: req.user.credits < 1 كيرجع 403 (402 محجوز فالـ spec) وكيرفض الطلب من الأصل.[8]

3. مراجعة: من درس الـ production routing، شنو كيدير catch-all app.get('*')؟

الـ catch-all هو آخر حل: إلا ما لقاش route handler ولا ملف داخل client/build، كيرجع index.html وكيسلّم الـ path للـ client-side router.[2]

4. شنو الفرق بين _user و recipients فـ survey schema؟

_user هو ObjectId بـ ref: 'user' بين جوج collections، أما recipients فداخلية فـ الـ survey كـ subdocuments.[6]
